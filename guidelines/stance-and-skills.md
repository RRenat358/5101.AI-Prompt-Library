# Стойки и Skills: расширенный гайд по композиции ролей

> **Область действия.** Этот гайд — для сложных композитов: одна стойка (Role)
> + knowledge-Skills, потенциальный конфликт стоек. Для таксономии и правил
    > именования — см. `entity-taxonomy.md`. Для простых композиций (Role +
    > Behavior/Format) — `role-plugin.md`.

## Преамбула: зачем это нужно

Основной гайд (`role-plugin-guide.md`) покрывает простой случай: одна роль +
поведенческие плагины (Критик, Ролевик и т.п.). Этого достаточно, пока:
- в композите одна стойка;
- пакеты несут только поведение (или только знание, но не смешиваются).

Проблемы начинаются, когда:
1. Хочется соединить роли с разной диспозицией (Разработчик «построй» +
   DevOps «автоматизируй») — модель начинает колебаться между дефолтами.
2. Пакетов становится много, и по имени не понять — это поведение или знание.
3. База и глубина смешиваются: роль либо отказывается отвечать (нет маркера
   области), либо разбавляется (техники вшиты прямо в роль).

Этот гайд описывает расширенную архитектуру: **одна стойка + knowledge-Skills**.
Он не заменяет основной гайд, а дополняет его для сложных случаев.

**Простое правило.** Если композит — это одна роль + Критик/Ролевик — основного
гайда достаточно. Если в композите больше двух пакетов или пакеты разной природы —
читайте этот гайд.


============================================================
## 1. Стойка (Stance)

**Определение.** Стойка — это дефолт ответа и приоритет роли. Не список
навыков, не тон, а то, **что модель делает по умолчанию**, когда задача
неоднозначна.

Стойки в ИТ:
- **Разработчик**: «построй». На вопрос «как сделать X» начинает с архитектуры и кода.
- **DevOps**: «автоматизируй». На вопрос о ручной операции предлагает автоматизацию.
- **АвтоТестировщик**: «строй надёжную систему, которая находит дефекты».
  Не «найди дефект» (ручной тестировщик) и не «построй» (разработчик) —
  специфическая диспозиция: тестируемость, покрытие, воспроизводимость.
- **Тестировщик (ручной)**: «найди дефект». Ищет, что может сломаться.
- **Сисадмин**: «сделай». На вопрос «что делать с X» даёт пошаговое решение.
- **Безопасник**: «сначала оцени риск, потом сделай».
- **LLM-эксперт**: «спроектируй промт/систему».

**Ключевое свойство: стойка ОДНА на композит.**


============================================================
## 2. Конфликт стоек — главная проблема

### Мини-пример: [Разработчик + DevOps]

Запрос: «Как задеплоить приложение?»

- **Разработчик (стойка «построй»)**: «Напиши Dockerfile, вот entry point,
  вот структура проекта, вот как собрать образ».
- **DevOps (стойка «автоматизируй»)**: «Вот pipeline: стадии build → test →
  deploy, вот secrets management, вот окружения».

Оба ответа про деплой, но с разной диспозицией. В композите [Разработчик +
DevOps] модель будет колебаться: то фокус на коде приложения, то на
инфраструктуре. В зависимости от формулировки запроса — то один ответ, то
другой. Нестабильно.

### Что делать вместо этого

Взять **одну стойку** + **knowledge-skill**, который содержит и технику, и
подводные камни.

- Стойка: DevOps.
- Skill: «Docker-деплой» — типичные стадии, secrets management, антипаттерны,
  что нельзя тащить в образ.
- Результат: DevOps отвечает в своём дефолте (автоматизация), но с глубиной.

### Почему «сначала оцени риск» — не skill

Потому что это **practice** (предписание поведения), то есть стойка. Даже без
«Ты — …» она вступает в конфликт с базовой стойкой.


============================================================
## 3. Классификация: knowledge vs practice

**Knowledge-skill** — знание: техники, чек-листы, подводные камни, примеры,
команды. Stance-neutral. Может подключаться к любой роли.

**Practice** — предписание поведения: «сначала оцени риск», «всегда пиши тесты»,
«сделай hardening». Это стойка. Живёт в роли (базовая стойка) или в
поведенческом плагине (Критик, Ролевик). **Не существует как отдельный класс
skill.** Если кто-то пишет «practice-skill» — это ошибка архитектуры.

**Тест на классификацию:**
> Если убрать пакет — **возьмётся ли модель за задачу**?
> - Возьмётся, но хуже/менее глубоко → knowledge-skill.
> - Перестанет браться или сменит стойку → practice, место в роли/плагине.

### Мини-пример: АвтоТестировщик

**Плохой пакет (это practice):**
```
[SKILL: Тестирование]
Всегда пиши тесты на каждую функцию.
```
Подключён реактивно к Психологу (плагином). Психолог начнёт требовать тесты
и давать сухие чек-листы, забыв про эмпатию. Стойка Психолога сломана.

**Хороший пакет (knowledge):**
```
[SKILL: Тестирование]
- Пирамида тестирования: что покрывать юнитами vs интеграционными vs e2e.
- Чек-лист покрытия для CRUD-эндпоинта.
- Антипаттерны: тесты, зависящие от порядка; тесты с общими фикстурами; sleeps.
```
Stance-neutral. Подключается к любой роли без конфликта.

## 4. База роли vs Дополнение (глубина)

**База роли** — минимальный набор, при котором роль идентифицируется и не
отказывается от задачи. Выражается маркерами: 1 строка, существительное,
без техник.

**Дополнение (skill)** — техники, чек-листы, подводные камни. 5–20 строк,
содержит конкретику.

**Операционный тест:**
> Если убрать — роль откажется отвечать или сменит рамку? → база.
> Роль ответит, но менее корректно/глубоко? → skill.

### Мини-пример: Разработчик

База:
- пишет код, архитектура приложений;
- CI/CD (маркер);
- security (маркер).

Запрос «напиши login» — базовая роль справится на уровне «работает».
+ Skill «Аутентификация» — уровень «работает и безопасно»: сессии vs токены,
  MFA, инвалидация, чек-лист аудита.

Разница — качество, не факт ответа. Тест: без skill ответит, но хуже → skill.

### Мини-пример: АвтоТестировщик

База:
- тестирование (ручное и автоматизированное);
- написание автотестов на языке проекта (маркер);
- CI/CD (маркер);
- LLM-агенты в тестировании (маркер).

Нужна глубина по CI/CD — Skill «CI-CD-pipelines». Это **не импорт базы
DevOps**, это углубление собственного CI/CD-маркера.

Нужна глубина по Java-тестам — Skill «Java-тестирование». Не импорт базы
Разработчика.

**Важный инсайт.** Сквозные маркеры (security, сохранность данных) должны быть
в базе каждой ИТ-роли одной строкой. Тогда вопрос «а как же база?» исчезает:
база уже есть у всех.


============================================================
## 5. АвтоТестировщик: не сборка, а отдельная стойка

**Соблазн:** собрать [Тестировщик + Разработчик + DevOps + LLM-эксперт] —
четыре роли в одном промте.

**Проблема:** четыре стойки. Тестировщик «найди дефект», Разработчик «построй»,
DevOps «автоматизируй», LLM-эксперт «спроектируй промт». Разные дефолты,
конфликт.

**Решение:** АвтоТестировщик — **своя стойка** «строй надёжную систему, которая
находит дефекты». Не сумма четырёх, а специфическая диспозиция. В базе — маркеры
четырёх областей (1 строка каждый). Skills — углубления по необходимости.

**Потенциальная проблема:** если АвтоТестировщик + 2 Skills станет слишком
большим (50+ строк), начнётся разбавление внимания. Тогда — делить не по
стойкам, а по задачам: «АвтоТестировщик-код» и «АвтоТестировщик-инфра».
Не сейчас, но имейте в виду.

## 6. Правила сборки композита

**Порядок блоков:**
1. Стойка (ЯДРО РОЛИ).
2. Критичные правила (если есть).
3. Маркеры областей (база роли).
4. Skills (knowledge).
5. Поведенческие плагины (Критик, Ролевик).

Причина: критичное — в первой четверти (урок из LLM-эксперта). Skills — после
базы, чтобы не разбавлять стойку.

**Правила:**
- Одна стойка на композит. Нужны две — это не композит, а другая роль.
- Skill не редактируется внутри композита. Правится Skill-источник → композит
  пересобирается.
- В шапке композита — версии встроенных пакетов. Пример:
  `// встроено: Skill "Аутентификация" @ 20261104-1200`.
- Сквозные маркеры в базе каждой роли (security, сохранность данных).

## 7. Мини-пример: один Skill, три роли

Skill «Docker-диагностика»:
- Разработчик + Skill — локальная среда не собирается.
- DevOps + Skill — pipeline падает на build.
- АвтоТестировщик + Skill — тесты не поднимаются в контейнере.

Один файл, три композита. DRY.

## 8. Чек-лист перед сборкой композита

- [ ] Одна стойка?
- [ ] Все пакеты — knowledge-skill (practice убраны в роль/плагин)?
- [ ] Сквозные маркеры в базе роли?
- [ ] Порядок: стойка → правила → маркеры → skills → плагины?
- [ ] Тип каждого пакета ясен (skill vs practice vs plugin)?
- [ ] Версии зафиксированы в шапке?
- [ ] Композит оправдан (используется 2+ раза)?
- [ ] Размер композита разумный (< 80 строк)?


============================================================
## 9. Когда НЕ использовать этот подход

- Одна роль + один поведенческий плагин — основного гайда достаточно.
- Разные роли для разных задач — просто разные файлы, без композитов.
- Skill не переиспользуется — вшить в роль, не создавать файл.
- Комбинация используется 1 раз — реактивно через плагин в диалоге.
