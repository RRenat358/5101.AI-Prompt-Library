# Таксономия сущностей промт-библиотеки

## Зачем этот файл

Библиотека содержит разнородные артефакты: роли, знания, поведения, форматы,
задачи, контейнеры, сборки. Без фиксированного словаря:
- непонятно, куда класть новый файл;
- непонятно, можно ли использовать файл самостоятельно;
- композиты собираются «на глаз», и стойка уплывает;
- при правке файла неясно, есть ли у него дубль в другом каталоге.

Этот файл задаёт словарь и правила размещения. Он не заменяет гайды
(`role-plugin.md`, `stance-and-skills.md`), а служит их основанием.

**Правило первого порядка:** каждый файл имеет ровно один тип из семи. Если файл
не относится ни к одному — это Snippets (§6a) или мусор (`archive/`).


============================================================
## 1. Семь сущностей

| # | Сущность | Что это | Меняет ли стойку | Самостоятельна |
|---|---|---|---|---|
| 1 | **Role** | Идентичность: «Ты — …» + база (маркеры областей) + стойка | задаёт | да |
| 2 | **Skill** | Знание: техники, чек-листы, подводные камни. Stance-neutral | нет | нет |
| 3 | **Behavior** | Предписание поведения/тона: «мысли как скептик», «будь коллегой» | да (или задаёт тон) | ограниченно (§5) |
| 4 | **Format** | Правила оформления вывода: тильда-блоки, структура, разбиение | нет | нет |
| 5 | **Action** | Задача/операция: «создай снимок», «сегментируй диалог» | нет (задаёт операцию) | да |
| 6 | **Wrapper** | Контейнер для добавления инструкций в идущем диалоге | нет | нет |
| 7 | **Composite** | Материализованная сборка Role + Skill(s) + Behavior(s) + Format(s) + Action(s) | наследует от Role | да |

**Пояснения.**

- **Role** задаёт стойку — дефолт ответа. Одна роль = одна стойка.
- **Skill** не меняет стойку: убрать → модель всё равно возьмётся за задачу,
  но ответ будет менее глубоким. Это операционный тест.
- **Behavior** может менять стойку (Критик) или только тон (Коллега). Поэтому
  «ограниченно самостоятелен» — §5.
- **Action** — операция, не идентичность. Отвечает на «что сделай».
- **Wrapper** — контейнер, не самостоятельная единица.


============================================================
## 2. Standalone vs add-on

**Standalone** (используется в начале диалога как есть):
- Role
- Action
- Composite

**Add-on** (используется только в составе Role/Composite или в середине диалога
через Wrapper):
- Skill
- Behavior
- Format

**Wrapper** — контейнер, не самостоятельная единица.

Статус определяется каталогом и суффиксом. Файл в `skills/`, `behaviors/`,
`formats/`, `wrappers/` — add-on. Файл в `roles/`, `actions/`,
`prompt-composites/` — standalone.


============================================================
## 3. Одна сущность = один файл = один тип

Два файла с почти одинаковым содержимым создают ловушку: правишь один,
забываешь другой.

**Правило по умолчанию:** содержимое существует в одном файле. Если нужны две
формы — вторая форма не дублирует содержание, а ссылается или является тонкой
обёрткой.

**Исключение — двойники Behavior (standalone vs add-on).** Допускается держать
два файла в `behaviors/`, если:

- первичный — `<имя>.BEHAVIOR.txt` (форма «Мыслишь как …», без «Ты — …»);
- standalone-двойник — `<имя>.txt` (форма «Ты — …», полное содержание);
- **в шапке обоих** — метка: `// синхронизировано с <имя>.BEHAVIOR.txt @ <версия>`;
- при правке одного — grep по `синхронизировано с` и обновить пару.

Двойник без метки синхронизации — запрещён: это гарантированный дрейф.


============================================================
## 4. Одна стойка на композит

В композите — ровно одна стойка (Role). Добавление Behavior допустимо, если он
не меняет стойку. Подробнее — `stance-and-skills.md`.


============================================================
## 5. Behavior как самостоятельная рамка

Два допустимых способа:

**Способ A (предпочтительный):** единственный источник —
`behaviors/<имя>.BEHAVIOR.txt`. Standalone-версия —
`prompt-composites/<имя>.Standalone.txt`: минимальная обёртка («Ты — ассистент»)
+ полный текст Behavior.

**Способ B (допустимый, с оговоркой):** два файла в `behaviors/` —
`<имя>.BEHAVIOR.txt` и `<имя>.txt`, с меткой синхронизации (§3).

**Правило:** Behavior никогда не содержит «Ты — …». Идентичность добавляется
вне Behavior.


============================================================
## 6. Организация каталогов

**Принцип: сущность первична, тема вторична.** Файл имеет первичную суть —
тип (Role, Skill, …). Тема — вторичный признак, выражается каталогом темы.

```text
prompts/                  # единичные сущности
  actions/
  behaviors/
  formats/
  roles/
  skills/
prompt-composites/        # собранные сборки
prompt-snippets/          # общие сниппеты
prompt-wrappers/          # контейнеры
prompt-by-theme/          # тематические витрины
  it/
  it-llm/
  psychology/
  spirituality/
  education/
  writing/
guidelines/               # правила и гайды
docs/                     # справочные материалы
archive/                  # разобранное / устаревшее
```

**Почему мета-контейнеры на корне.** `prompts/` — чистый «склад единичных
сущностей». Всё собранное, сгруппированное и служебное — на уровень выше,
с префиксом `prompt-`. Это визуально отделяет сущность от мета и упрощает
навигацию: открыл `prompts/` — видишь только роли/скиллы/бихевиоры.


============================================================
## 6a. Правило темы в `prompt-by-theme/`

**Тема создаётся, когда выполнены оба условия:**

1. **≥2 артефакта** (Role, Skill, Behavior, Format, Action, Snippets)
   тематически связаны и используются вместе.
2. **Связь устойчива:** файлы образуют рабочий набор, а не случайное соседство.

**Sidecar-документация не считается артефактом.** `Роль.txt` + `Роль.GUIDE.txt`
= 1 артефакт, темы нет.

**Композиты не считаются артефактами темы.** Они живут в `prompt-composites/`.

**Общие файлы не дублируются в теме.** Если Skill используется и вне темы —
он остаётся в `prompts/skills/`.

**Внутри темы:**

- файлы лежат плоско, если одного типа < 3;
- подпапка сущности (`roles/`, `skills/`, `actions/`) создаётся, если файлов
  этого типа ≥ 3;
- в плоском каталоге темы файл **без суффикса** — это Role; остальные — с
  суффиксом (§7).

**Имя темы.** Составные темы — через тире: `it-llm`, `it-qa`. Не через точку
(ломает иерархию в IDE и скриптах) и не через подчёркивание (не часть
конвенций автора). Дефис — рабочее решение; при росте числа IT-тем (>6)
рассмотреть переход на `it/` с подпапками.


============================================================
## 6b. Snippets — мета-тип, не сущность

**Snippets** — файл с набором нано-инструкций (1–2 предложения), сгруппированных
по теме. Не является Role/Skill/Behavior/Format/Action целиком: может содержать
элементы разных типов в миниатюре; используется построчно.

**Зачем:** дробить 20 нано-инструкций на 20 файлов — хуже, чем один сборник:
много файлов с нано-содержимым трудно просматривать.

**Правила:**
- Имя: `<тема>.SNIPPETS.txt`.
- **Привязка к сущности.** Если сборник тематически про одну сущность
  (поведение, формат) — лежит в папке этой сущности: `behaviors/<имя>.SNIPPETS.txt`,
  `formats/<имя>.SNIPPETS.txt`. Если сборник общий, вне одной сущности —
  в `prompt-snippets/`.
- Внутри — маркированные мини-инструкции, каждая самодостаточна.
- Не участвует в сборке композитов автоматически.

Snippets — **не восьмая сущность**. Это контейнер, как Wrapper, но для
нано-инструкций.


============================================================
## 7. Правила именования

| Сущность | Суффикс | Пример |
|---|---|---|
| Role | без суффикса | `Сисадмин.Универсальный.txt`, `Разработчик.Base.txt` |
| Skill | `.SKILL` (только в плоском каталоге темы) | `Критический-анализ-в-психологии.SKILL.txt` |
| Behavior | `.BEHAVIOR` (в `behaviors/` — обязателен для двойников) | `Критик-аналитик.BEHAVIOR.txt` |
| Format | `.FORMAT` (только в плоском каталоге темы) | `Тильда-блок.FORMAT.txt` |
| Action | `.ACTION` (только в плоском каталоге темы) | `Гуманизация-текста-ИИ.ACTION.txt` |
| Wrapper | `.WRAPPER` (только в плоском каталоге) | — |
| Composite | без суффикса, сегменты через `.` | `Психолог.Критик.txt` |
| Snippets | `.SNIPPETS` (всегда) | `LLM.SNIPPETS.txt` |
| Guide (sidecar) | `.GUIDE` (всегда) | `Timestamp.GUIDE.txt` |

**Два правила, из которых всё следует:**

1. **В папке своей сущности — без суффикса.** `skills/Тестирование.txt`,
   `roles/Политик-аналитик.txt`, `actions/Контекстный-снимок.txt`. Папка уже
   сказала тип — суффикс был бы маслом.
2. **В плоском каталоге — с суффиксом.** `-by-theme/psychology/Психолог-аналитик.txt`
   (Role — без), `Критический-анализ-в-психологии.SKILL.txt` (Skill — с).
   Здесь суффикс — единственный признак типа.

**Role — без суффикса всегда.** Это дефолтный тип. Отсутствие суффикса = Role.
Правило делает суффиксы однозначными: «есть капс-суффикс — не Role».

**Исключение — `behaviors/`.** Там двойники (`.BEHAVIOR.txt` + `.txt`), поэтому
первичный файл оставляем с суффиксом, чтобы отличить от двойника.

**Капс — только для промт-экосистемы.** `.SKILL`, `.BEHAVIOR`, `.FORMAT`,
`.ACTION`, `.WRAPPER`, `.SNIPPETS`, `.GUIDE` — это части промтов и их
документации, они читаются LLM как контекст. Строчными — только внешняя
документация (`docs/`, `guidelines/*.md`). `README.md` — капсом по конвенции,
независимо от расположения.


============================================================
## 8. Документация и sidecar-файлы

Документация (`.GUIDE`, `.README.md`) — не сущность, но может лежать рядом с
мишенью (sidecar). Причина: гайд к файлу должен быть виден при работе с файлом,
а не теряться в общей папке.

**Правила sidecar:**
- Имя повторяет имя мишени: `<мишень>.GUIDE.txt`, `<мишень>.README.md`.
- Лежит в том же каталоге, что мишень.
- **Не участвует в сборке композитов.**
- Не считается артефактом при подсчёте правила темы (§6a).
- Общие гайды (не привязанные к одной мишени) — в `guidelines/` или `docs/`.


============================================================
## 9. Чек-лист при добавлении файла

- [ ] Тип определён (Role / Skill / Behavior / Format / Action / Wrapper /
  Composite / Snippets / Guide)?
- [ ] Standalone или add-on? (§2)
- [ ] Файл лежит в папке своего типа или в `prompt-by-theme/<тема>/`?
- [ ] Если в папке сущности — без суффикса (кроме двойников Behavior)?
- [ ] Если в плоском каталоге темы — с суффиксом (кроме Role)?
- [ ] Если Behavior-двойник — метка синхронизации в шапке? (§3)
- [ ] Если Skill — stance-neutral? (тест: убрать → модель берётся за задачу)
- [ ] Если Action — первичная природа операция, а не идентичность?
- [ ] Если Composite — стойка одна? Версии встроенных add-on в шапке?
- [ ] Если Snippets — нано-инструкции самодостаточны? Привязан к сущности
  или общий? (§6b)
- [ ] Если тема — ≥2 артефакта? Sidecar и композиты не в счёте? (§6a)
- [ ] Документация — `.GUIDE`/`.README.md` рядом с мишенью? (§8)


============================================================
