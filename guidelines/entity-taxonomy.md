# Таксономия сущностей промт-библиотеки

## Зачем этот файл

Библиотека содержит разнородные артефакты: роли, знания, поведения, форматы,
задачи, контейнеры, сборки. Без фиксированного словаря:
- непонятно, куда класть новый файл;
- непонятно, можно ли использовать файл самостоятельно;
- композиты собираются «на глаз», и стойка уплывает;
- при правке файла неясно, есть ли у него дубль в другом каталоге.

Этот файл задаёт словарь из семи сущностей и правила размещения. Он не заменяет
гайды (`role-plugin-guide.md`, `stance-and-skills-guide.md`), а служит их
основанием.

**Правило первого порядка:** каждый файл имеет ровно один тип из семи. Если файл
не относится ни к одному — это Snippets (§6a) или мусор (`archive/`).


============================================================
## 1. Семь сущностей

| # | Сущность | Что это | Меняет ли стойку | Самостоятельна |
|---|---|---|---|---|
| 1 | **Role** | Идентичность: «Ты — …» + база (маркеры областей) + стойка | задаёт | да |
| 2 | **Skill** | Знание: техники, чек-листы, подводные камни. Stance-neutral | нет | нет |
| 3 | **Behavior** | Предписание поведения/тона: «мысли как скептик», «будь коллегой» | да (или задаёт тон) | ограниченно (§5) |
| 4 | **Format** | Правила оформления вывода: тильда-блоки, структура, разбиение | нет | нет |
| 5 | **Action** | Задача/операция: «создай снимок», «сегментируй диалог» | нет (задаёт операцию) | да |
| 6 | **Wrapper** | Контейнер для добавления инструкций в идущем диалоге | нет | нет |
| 7 | **Composite** | Материализованная сборка Role + Skill(s) + Behavior(s) + Format(s) + Action(s) | наследует от Role | да |

**Пояснения.**

- **Role** задаёт стойку — дефолт ответа. Одна роль = одна стойка.
- **Skill** не меняет стойку: убрать → модель всё равно возьмётся за задачу,
  но ответ будет менее глубоким. Это операционный тест.
- **Behavior** может менять стойку (Критик) или только тон (Коллега). Поэтому
  «ограниченно самостоятелен» — §5.
- **Action** — операция, не идентичность. Отвечает на «что сделай».
- **Wrapper** — контейнер, не самостоятельная единица.


============================================================
## 2. Standalone vs add-on

**Standalone** (используется в начале диалога как есть):
- Role
- Action
- Composite

**Add-on** (используется только в составе Role/Composite или в середине диалога
через Wrapper):
- Skill
- Behavior
- Format

**Wrapper** — особый случай: контейнер, не самостоятельная единица.

**Следствие:** статус определяется каталогом и суффиксом. Файл в `skills/`,
`behaviors/`, `formats/`, `wrappers/`, `snippets/` — add-on. Файл в `roles/`,
`actions/`, `prompt-composites/` — standalone.


============================================================
## 3. Одна сущность = один файл = один тип

Два файла с почти одинаковым содержимым, где один — «роль», другой — «плагин»,
создают ловушку: правишь один, забываешь другой.

**Правило по умолчанию:** содержимое существует в одном файле. Если нужны две
формы — вторая форма не дублирует содержание, а ссылается или является тонкой
обёрткой.

**Исключение — двойники Behavior (standalone vs add-on).** Для поведений
(Критик, Коллега) допускается держать два файла в `behaviors/`, если:

- первичный — `<имя>.BEHAVIOR.txt` (форма «Мыслишь как …», без «Ты — …»);
- standalone-двойник — `<имя>.txt` (форма «Ты — …», полное содержание);
- **в шапке обоих** — метка синхронизации:
  `// синхронизировано с behaviors/<имя>.BEHAVIOR.txt @ <версия>`;
- при правке одного — grep по `синхронизировано с` и обновить пару.

Двойник без метки синхронизации — запрещён: это гарантированный дрейф.


============================================================
## 4. Одна стойка на композит

В композите — ровно одна стойка (Role). Добавление Behavior допустимо, если он
не меняет стойку. Подробнее — `stance-and-skills-guide.md`.


============================================================
## 5. Behavior как самостоятельная рамка

Два допустимых способа:

**Способ A (предпочтительный):** единственный источник —
`behaviors/<имя>.BEHAVIOR.txt`. Standalone-версия —
`prompt-composites/<имя>.Standalone.txt`: минимальная обёртка («Ты — ассистент»)
+ полный текст Behavior.

**Способ B (допустимый, с оговоркой):** два файла в `behaviors/` —
`<имя>.BEHAVIOR.txt` и `<имя>.txt`, с меткой синхронизации (§3).

**Правило:** Behavior никогда не содержит «Ты — …». Идентичность добавляется
вне Behavior.


============================================================
## 6. Организация каталогов

**Принцип: сущность первична, тема вторична.** Файл имеет первичную суть —
тип (Role, Skill, …). Тема — вторичный признак, выражается каталогом темы или
тегом.

**Структура, пример:**

```
prompts/
  -by-theme/
    it/
    it-llm/
    psychology/
    education/
    writing/
    ...
  actions/
  behaviors/
  formats/
  roles/
  skills/
  snippets/
  wrappers/
prompt-composites/
guidelines/
docs/
archive/
```

**Правила.**

1. **Корневые каталоги сущностей** (`roles/`, `skills/`, …) — для единичных
   файлов вне тем и для файлов, чья тема не набрала 3+ файлов.
2. **`-by-theme/`** — витрина для частых тем. Внутри темы:
  - файлы лежат плоско, если одного типа < 3;
  - подпапка сущности (`roles/`, `skills/`, `actions/`) создаётся, если файлов
    этого типа ≥ 3.
  - Файлы в теме **не дублируют** корневые каталоги; это те же файлы, но
    сгруппированные по теме. Файл существует в одном месте.
3. **Файл без суффикса** в `-by-theme/` — это Role. Всё остальное — с суффиксом
   (§7). Правило позволяет не писать `.ROLE` для каждого файла.
4. **Тема без 3+ файлов** не создаёт папку в `-by-theme/`. Её файлы живут в
   корневых каталогах сущностей.

**Почему `-by-theme/` — не вторая иерархия.** Внутри темы нет полного набора
подпапок сущностей; есть только те, что реально используются. Тема — это
«полка», а не «шкаф». Если тема вырастет и потребует полной структуры — она
переезжает в отдельный подпроект (как `psychology/` потенциально).

## 6a. Snippets — мета-тип, не сущность

**Snippets** — файл с набором нано-инструкций (1–2 предложения), сгруппированных
по теме. Не является Role/Skill/Behavior/Format/Action целиком:
- может содержать элементы разных типов в миниатюре;
- используется не целиком, а построчно — берут нужную инструкцию.

**Зачем:** дробить 20 нано-инструкций на 20 файлов — хуже, чем один сборник:
много файлов с нано-содержимым трудно просматривать.

**Правила:**
- Имя: `<тема>.SNIPPETS.txt` (например, `LLM.SNIPPETS.txt`).
- Место: `snippets/` в корне или в теме.
- Внутри — маркированные мини-инструкции, каждая самодостаточна.
- Не участвует в сборке композитов автоматически.

Snippets — **не восьмая сущность**. Это контейнер, как Wrapper, но для
нано-инструкций.


============================================================
## 7. Правила именования

| Сущность | Суффикс | Пример |
|---|---|---|
| Role | без суффикса | `Сисадмин.Универсальный.txt`, `Разработчик.Base.txt` |
| Skill | `.SKILL` | `Security.Auth.SKILL.txt`, `Тестирование.SKILL.txt` |
| Behavior | `.BEHAVIOR` | `Критик-аналитик.BEHAVIOR.txt` |
| Format | `.FORMAT` | `Тильда-блок.FORMAT.txt`, `Timestamp.FORMAT.txt` |
| Action | `.ACTION` | `Контекстный-снимок.ACTION.txt` |
| Wrapper | `.WRAPPER` | `Плагин-дополнительных-инструкций.WRAPPER.txt` |
| Composite | без суффикса, сегменты через `.` | `Психолог.Критик.txt` |
| Snippets | `.SNIPPETS` | `LLM.SNIPPETS.txt` |

**Суффикс — капсом.** Причина: `.Behavior` сливается с именем, `.BEHAVIOR` —
читается как тип. Суффикс — это маркер, а не часть имени.

**Role — без суффикса.** Причина: это дефолтный тип в `roles/` и в темах.
Отсутствие суффикса = Role. Это делает суффиксы однозначными.

**Тип файла также задаётся заголовком блока** (`[ROLE: …]`, `[SKILL: …]`,
`[BEHAVIOR: …]`). Суффикс и заголовок дублируют друг друга — это допустимо:
суффикс виден в `ls`, заголовок — в содержимом.


============================================================
## 8. Документация и sidecar-файлы

Документация (`.md`, `.guide.txt`, `.README.md`) — не сущность, но может лежать
**рядом с мишенью** (sidecar). Причина: гайд к файлу должен быть виден при
работе с файлом.

**Правила sidecar:**
- Имя повторяет имя мишени: `<мишень>.README.md`, `<мишень>.guide.txt`.
- Лежит в том же каталоге, что мишень.
- **Не участвует в сборке композитов.**
- Общие гайды — в `guidelines/` или `docs/`.


============================================================
## 9. Чек-лист при добавлении файла

- [ ] Тип определён (Role / Skill / Behavior / Format / Action / Wrapper /
  Composite / Snippets)?
- [ ] Standalone или add-on? (§2)
- [ ] Файл лежит в каталоге своего типа или в `-by-theme/<тема>/`?
- [ ] Если в теме — файл без суффикса (Role) или с суффиксом (не Role)?
- [ ] Если Behavior-двойник — метка синхронизации в шапке? (§3)
- [ ] Если Skill — stance-neutral? (тест: убрать → модель берётся за задачу)
- [ ] Если Action — первичная природа операция, а не идентичность?
- [ ] Если Composite — стойка одна? Версии встроенных add-on в шапке?
- [ ] Нет брата-близнеца без метки синхронизации? (§3)
- [ ] Если Snippets — нано-инструкции самодостаточны? (§6a)
- [ ] Документация — sidecar рядом с мишенью? (§8)
