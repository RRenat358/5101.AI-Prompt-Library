# Таксономия сущностей промт-библиотеки

Этот файл задаёт словарь и правила размещения. Он не заменяет гайды
([role-plugin.md](role-plugin.md), [stance-and-skills.md](stance-and-skills.md)),
а служит их основанием.

**Зачем это нужно.** Библиотека растёт, и без общего словаря начинается
знакомое: новый файл — новый вопрос «куда его?», композиты собираются на глаз,
при правке одного файла неясно, есть ли у него близнец в другом каталоге. Здесь
— ответы на эти вопросы в одном месте.

**Правило первого порядка.** Каждый файл имеет ровно один тип из семи. Не
относится ни к одному — это Snippets (§6b) или мусор (`archive/`).


============================================================
## 1. Семь сущностей

Перечисление по алфавиту — чтобы не перестраивать при добавлении или удалении
типа.

| # | Сущность | Что это | Меняет ли стойку | Самостоятельна |
|---|---|---|---|---|
| 1 | **Action** | Задача/операция: «создай снимок», «сегментируй диалог» | нет (задаёт операцию) | да |
| 2 | **Behavior** | Предписание поведения/тона: «мысли как скептик», «будь коллегой» | да (или задаёт тон) | ограниченно (§5) |
| 3 | **Composite** | Материализованная сборка Role + Skill(s) + Behavior(s) + Format(s) + Action(s) | наследует от Role | да |
| 4 | **Format** | Правила оформления вывода: тильда-блоки, структура, разбиение | нет | нет |
| 5 | **Role** | Идентичность: «Ты — …» + база (маркеры областей) + стойка | задаёт | да |
| 6 | **Skill** | Знание: техники, чек-листы, подводные камни. Stance-neutral | нет | нет |
| 7 | **Wrapper** | Контейнер для добавления инструкций в идущем диалоге | нет | нет |

**Пояснения.**

- **Action** — операция, не идентичность. Отвечает на «что сделай», не «кто ты».
- **Behavior** может менять стойку (Критик) или только тон (Коллега). Поэтому
  «ограниченно самостоятелен» — §5.
- **Composite** — сборка с одной стойкой. Две стойки в одном композите
  запрещены (§4).
- **Role** задаёт стойку — дефолт ответа. Одна роль = одна стойка.
- **Skill** не меняет стойку: убрать → модель всё равно возьмётся за задачу, но
  ответ будет менее глубоким. Это операционный тест.
- **Wrapper** — контейнер, не самостоятельная единица.


============================================================
## 2. Standalone vs add-on

Перечисление по алфавиту.

**Add-on** — используется только в составе Role/Composite или в середине
диалога через Wrapper:
- Behavior
- Format
- Skill

**Standalone** — можно вставить в начало диалога как есть:
- Action
- Composite
- Role

**Wrapper** — контейнер, не самостоятельная единица.

Статус определяется каталогом и суффиксом. Файл в `skills/`, `behaviors/`,
`formats/`, `wrappers/` — add-on. Файл в `roles/`, `actions/`,
`prompt-composites/` — standalone.


============================================================
## 3. Одна сущность = один файл = один тип

Два файла с почти одинаковым содержимым — ловушка: правишь один, забываешь
другой. Поэтому по умолчанию содержимое живёт в одном файле. Нужны две формы —
вторая не дублирует содержание, а ссылается или является тонкой обёрткой.

**Двойники допустимы, но с меткой.** Если две формы всё же держатся рядом
(например, Behavior и его standalone-роль-версия), в шапке **обоих** файлов
стоит метка синхронизации:

```text
// синхронизировано с <имя>.<сущность>.txt @ <версия>
```

При правке одного — grep по `синхронизировано с` и обновить пару. Двойник без
метки — запрещён: это гарантированный дрейф.

**Кто дефолт, а кто инородец — решает папка.** В `behaviors/` дефолт — Behavior
(без суффикса), а standalone-роль — инородец с суффиксом `.ROLE`. В `roles/` —
наоборот. Это одно правило вместо двух (§7).


============================================================
## 4. Одна стойка на композит

В композите — ровно одна стойка (Role). Добавление Behavior допустимо, если он
не меняет стойку. Подробнее — [stance-and-skills.md](stance-and-skills.md).


============================================================
## 5. Behavior как самостоятельная рамка

Behavior и standalone-роль-версия — это две формы одного содержания. Чтобы не
держать двух источников:

**Способ A (предпочтительный).** Единственный источник —
`behaviors/<имя>.txt` (форма «Мыслишь как …», без «Ты — …»). Standalone-версия
— `prompt-composites/<имя>.Standalone.txt`: минимальная обёртка («Ты —
ассистент») + полный текст Behavior. При правке Behavior композит пересобирается.

**Способ B (допустимый, с оговоркой).** Два файла в `behaviors/`:
`<имя>.txt` (Behavior, дефолт) и `<имя>.ROLE.txt` (standalone-роль, инородец).
С меткой синхронизации в шапке обоих (§3).

Способ A — меньше обслуживания. Способ B — привычнее для чтения («Ты —
критик»). Выбор за автором, но метка синхронизации при B обязательна.

**Правило:** Behavior не содержит «Ты — …». Если форма содержит «Ты — …» — это
Role-версия, она живёт вне Behavior (в композите или с суффиксом `.ROLE`).


============================================================
## 6. Организация каталогов

**Принцип: сущность первична, тема вторична.** Файл имеет первичную суть — тип
(Role, Skill, …). Тема — вторичный признак, выражается каталогом темы.

**Пример структуры** (не догма — конкретные темы и файлы меняются):

```text
archive
docs
guidelines
prompt-by-theme
prompt-by-theme/education
prompt-by-theme/it
prompt-by-theme/it_llm
prompt-by-theme/psychology
prompt-by-theme/spirituality
prompt-by-theme/writing
prompt-composites
prompt-snippets
prompt-wrappers
prompts
prompts/actions
prompts/behaviors
prompts/formats
prompts/roles
prompts/skills
```

**Почему мета-контейнеры на корне.** `prompts/` — чистый склад единичных
сущностей. Всё собранное, сгруппированное и служебное — на уровень выше, с
префиксом `prompt-`. Открыл `prompts/` — видишь только роли/скиллы/бихевиоры.
Открыл корень — видишь всё, включая витрины и сборки.


============================================================
## 6a. Правило темы в `prompt-by-theme/`

Тема создаётся, когда выполнены **оба** условия:

1. **≥2 артефакта** (Action, Behavior, Format, Role, Skill, Snippets)
   тематически связаны и используются вместе.
2. **Связь устойчива** — файлы образуют рабочий набор, а не случайное соседство.

**Что не считается артефактом темы:**
- **Sidecar-документация** (`<мишень>.GUIDE.txt`, `<мишень>.README.md`).
  `Роль.txt` + `Роль.GUIDE.txt` = 1 артефакт, темы нет.
- **Композиты** — они живут в `prompt-composites/` независимо от темы.

**Общие файлы не дублируются.** Если Skill используется и вне темы — он
остаётся в `prompts/skills/`.

**Внутри темы:**
- файлы лежат плоско, если одного типа < 3;
- подпапка сущности (`actions/`, `behaviors/`, `formats/`, `roles/`, `skills/`)
  создаётся, если файлов этого типа ≥ 3;
- в плоском каталоге темы файл **без суффикса** — это Role; остальные — с
  суффиксом (§7).

**Имя темы.** Составные темы — через тире: `it-llm`, `it-qa`. Не через точку
(ломает иерархию в IDE и скриптах) и не через подчёркивание (не приживается).
Дефис — рабочее решение; при росте числа IT-тем (>6) рассмотреть переход на
`it/` с подпапками.

**Тег темы в шапке файла.** Тема — не только каталог, но и тег
(`tags: [it, role]`). Это даёт сквозной поиск: файлы одной темы находятся
строкой поиска, даже если лежат в разных сущностях. Подробнее —
[tagging-system.md](tagging-system.md).


============================================================
## 6b. Snippets — мета-тип, не сущность

**Snippets** — файл с набором нано-инструкций (1–2 предложения), сгруппированных
по теме. Не является Role/Skill/Behavior/Format/Action целиком: может содержать
элементы разных типов в миниатюре; используется построчно.

**Зачем:** дробить 20 нано-инструкций на 20 файлов — хуже, чем один сборник.
Много файлов с нано-содержимым трудно просматривать, а нужную инструкцию
приходится искать перебором.

**Правила:**
- Имя: `<тема>.SNIPPETS.txt`.
- **Привязка к сущности.** Если сборник тематически про одну сущность
  (поведение, формат) — лежит в папке этой сущности:
  `behaviors/<имя>.SNIPPETS.txt`, `formats/<имя>.SNIPPETS.txt`. Если общий,
  вне одной сущности — в `prompt-snippets/`.
- Внутри — маркированные мини-инструкции, каждая самодостаточна.
- Не участвует в сборке композитов автоматически.

Snippets — **не восьмая сущность**. Это контейнер, как Wrapper, но для
нано-инструкций.

## 7. Правила именования

Перечисление по алфавиту.

| Сущность | Суффикс | Пример |
|---|---|---|
| Action | `.ACTION` (только в плоском каталоге) | `Гуманизация-текста-ИИ.ACTION.txt` |
| Behavior | `.BEHAVIOR` (только в чужой папке) | `Коллега.BEHAVIOR.txt` |
| Composite | без суффикса, сегменты через `.` | `Психолог.Критик.txt` |
| Format | `.FORMAT` (только в плоском каталоге) | `Тильда-блок.FORMAT.txt` |
| Guide (sidecar) | `.GUIDE` (всегда) | `Timestamp.GUIDE.txt` |
| Role | `.ROLE` (только в чужой папке) | `Коллега.ROLE.txt` |
| Skill | `.SKILL` (только в плоском каталоге) | `Критический-анализ-в-психологии.SKILL.txt` |
| Snippets | `.SNIPPETS` (всегда) | `LLM.SNIPPETS.txt` |
| Wrapper | `.WRAPPER` (только в плоском каталоге) | — |

**Три правила, из которых всё следует.**

1. **В папке своей сущности — без суффикса.** `skills/Тестирование.txt`,
   `roles/Политик-аналитик.txt`, `actions/Контекстный-снимок.txt`. Папка уже
   сказала тип — суффикс был бы маслом.
2. **В плоском каталоге — с суффиксом.** `prompt-by-theme/psychology/`:
   `Психолог-аналитик.txt` (Role — без), `Критический-анализ-в-психологии.SKILL.txt`
   (Skill — с). Здесь суффикс — единственный признак типа.
3. **Инородец в чужой папке — с суффиксом своей сущности.** `behaviors/Коллега.txt`
   (Behavior, дефолт) и `behaviors/Коллега.ROLE.txt` (Role, инородец).
   `roles/Критик-аналитик.BEHAVIOR.txt` — Behavior в папке ролей.

**Role — без суффикса в `roles/` и в плоском каталоге темы.** Это дефолтный
тип. Отсутствие суффикса = Role. В чужой папке Role помечается `.ROLE`, потому
что там она инородец.

**Капс — только для промт-экосистемы.** `.ACTION`, `.BEHAVIOR`, `.FORMAT`,
`.GUIDE`, `.ROLE`, `.SKILL`, `.SNIPPETS`, `.WRAPPER` — это части промтов и их
документации, они читаются LLM как контекст. Строчными — только внешняя
документация (`docs/`, `guidelines/*.md`). `README.md` — капсом по конвенции,
независимо от расположения.


============================================================
## 8. Документация и sidecar-файлы

Документация (`.GUIDE`, `.README.md`) — не сущность, но может лежать рядом с
мишенью (sidecar). Причина простая: гайд к файлу должен быть виден при работе с
файлом, а не теряться в общей папке.

**Правила sidecar:**
- Имя повторяет имя мишени: `<мишень>.GUIDE.txt`, `<мишень>.README.md`.
- Лежит в том же каталоге, что мишень.
- **Не участвует в сборке композитов.**
- Не считается артефактом при подсчёте правила темы (§6a).
- Общие гайды (не привязанные к одной мишени) — в `guidelines/` или `docs/`.

## 9. Чек-лист при добавлении файла

- [ ] Тип определён (Action / Behavior / Composite / Format / Role / Skill /
  Wrapper / Snippets / Guide)?
- [ ] Standalone или add-on? (§2)
- [ ] Файл лежит в папке своего типа или в `prompt-by-theme/<тема>/`?
- [ ] Если в папке сущности — без суффикса (кроме инородцев из чужой папки)?
- [ ] Если в плоском каталоге темы — с суффиксом (кроме Role)?
- [ ] Если двойник — метка синхронизации в шапке обоих? (§3)
- [ ] Если Skill — stance-neutral? (тест: убрать → модель берётся за задачу)
- [ ] Если Action — первичная природа операция, а не идентичность?
- [ ] Если Composite — стойка одна? Версии встроенных add-on в шапке?
- [ ] Если Snippets — нано-инструкции самодостаточны? Привязан к сущности
  или общий? (§6b)
- [ ] Если тема — ≥2 артефакта? Sidecar и композиты не в счёте? (§6a)
- [ ] Документация — `.GUIDE`/`.README.md` рядом с мишенью? (§8)
- [ ] Тег темы проставлен в шапке? (§6a)
