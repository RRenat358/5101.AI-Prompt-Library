# Сборка Composite

> **Область действия.** Этот гайд — практическая механика сборки Composite:
> порядок блоков, именование, версии, синхронизация, тестирование. Концепция
> (что такое стойка, почему две стойки конфликтуют, knowledge vs practice) —
> в [stance-and-skills.md](stance-and-skills.md). Таксономия и правила
> размещения — в [entity-taxonomy.md](entity-taxonomy.md). Динамическое
> добавление в идущий диалог — в [role-plugin.md](dynamic-additions.md).

Composite — это файл-сборка, где все блоки заданы одновременно. Модель читает
его как единое целое с самого начала. Никаких «сохраняя текущую роль и
предыдущие настройки» — это для динамики, не для сборки.


============================================================
## 1. Когда Composite, а когда — динамически

Матрица решений:

| Ситуация                                                | Что выбрать               |
|---------------------------------------------------------|---------------------------|
| Разовая задача, один диалог                             | Динамически через обёртку |
| Комбинация используется 2+ раза                         | Composite                 |
| Просто: 1 Role + 1 Behavior                             | Динамически проще         |
| Сложно: 3+ блока, несколько Skills                      | Composite                 |
| Нужна фиксированная версия для повторного использования | Composite                 |

Composite оправдан, когда комбинация — это **рабочий инструмент**, а не
одноразовый эксперимент. Если сомневаетесь — начните с динамики, переведите в
Composite, когда почувствуете, что собираете одно и то же в третий раз.


============================================================
## 2. Что входит в Composite

- **Role** — обязательна, ровно одна. Задаёт стойку.
- **Skills** — 0+, knowledge, stance-neutral.
- **Behaviors** — 0+, не конфликтуют со стойкой.
- **Formats** — 0+.
- **Actions** — не входят. Action — самостоятельная единица, не add-on. Он
  либо заменяет Role целиком (тогда это не Composite, а Action), либо
  выполняется отдельно.
- **Wrapper** — **никогда**. Обёртка — для динамического добавления в идущем
  диалоге, в статической сборке она не нужна и создаёт шум.
- **Snippets** — не входят как блок. Отдельные нано-инструкции можно вплести
  в текст, но это уже ручная работа, не сборка.


============================================================
## 3. Порядок блоков

```
1. Ядро роли        [ЯДРО РОЛИ] + «Ты — …»
2. База роли        маркеры областей (1 строка каждый)
3. Критичные правила (если есть)
4. Skills           knowledge-углубления
5. Behaviors        practice, не меняющие стойку
6. Formats          оформление вывода
```

**Почему так.**

- **Критичное — в первой четверти.** Внимание модели сильнее в начале. Ядро,
  база и критичные правила идут первыми, чтобы не потеряться.
- **Skills до Behaviors.** Skill углубляет то, что Role уже делает. Behavior
  добавляет диспозицию. Сначала — углубление базы, потом — надстройка.
- **Formats в конце.** Оформление — последнее, что применяется к уже
  сформированному ответу.

Внутри групп (Skills, Behaviors) порядок — **по логике и значимости**, а не по
алфавиту. Например: сначала общий Критик, потом — специфический
Критический-анализ-в-психологии. Сначала базовый Skill, потом — углубляющий.

## 4. Именование Composite

Сегменты через точку, без суффикса (Composite — «своя папка»,
`prompt-composites/`).

**Role — всегда первая.** Остальные сегменты — по логике сборки: близость к
роли, порядок применения, значимость.

Примеры:

```
Психолог.Критик.txt
Психолог.Критик.КритикПсихологии.txt
Психолог.Критик.КритикПсихологии.Коллега.txt
LLM-эксперт.Ролевик.Критик.txt
```

**`.Standalone` для Behavior-as-standalone.** Если Behavior используется как
самостоятельная рамка — `Критик.Standalone.txt` (минимальная обёртка + Behavior).
Подробнее — §8.

Полные правила именования — [entity-taxonomy.md](entity-taxonomy.md), §7.

## 5. Версионирование

**Версия Composite = самая поздняя из версий встроенных add-on.** Пример:
аддоны с версиями `20210501`, `20240701`, `20260120`, `20250615` → версия
композита `20260120`.

Почему так: версия композита отражает «свежесть» его содержимого. Если хотя бы
один аддон обновлён — композит тоже считается обновлённым, даже если сам текст
сборки не менялся.

**Версия аддона** берётся из шапки исходного файла (`<имя>.<тип> @ <версия>`).
Если в исходнике версии нет — это пробел, стоит добавить.


### 5a. Мета-блок Composite

Общий формат мета-блока — [style.md](style.md), §2. 
Отличие для Composite — только в `description`: там перечисляется состав и версии встроенных модулей.

```
[мета: игнорируй всё до второй строки из символов `━`]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
title:       <Role> + <Addon1> + <Addon2>
version:     <самая поздняя из версий add-on>

tags:        #composite, #role    #<тема>    #ready
description: |
    Состав:
        1. <Role>.txt -- <версия>
        2. <Addon>.txt -- <версия>
        3. <Addon>.txt -- <версия>
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

- **Теги — группами через таб.** Первая группа — тип: `#composite` + тег того,
  что внутри (`#role`, `#action`, `#skill`…). Вторая — тема. Третья — статус.
- **`description` — только состав и версии**, формат `<имя>.txt -- <версия>`.
- **`.txt` в списке** — чтобы при пересылке файла вне репозитория было видно,
  что это сборка из файлов.

## 6. Синхронизация с источниками

Аддон обновился → какие композиты затронуты?

**Сейчас — ручная синхронизация.** Ответственный — админ репозитория. При правке
аддона:

1. Обновить версию в шапке аддона.
2. Grep по `встроено:` в `prompt-composites/` — найти композиты, где этот аддон
   упомянут.
3. В каждом затронутом композите — обновить версию аддона в шапке и, если
   содержание аддона изменилось, — встроенный текст.
4. Обновить версию Composite (по правилу §5 — самая поздняя из аддонов).

Автоматизация — возможна (скрипт-генератор шапок), но пока не делаем: ручной
grep работает, композитов немного. Когда их станет 30+ — вернёмся к вопросу.

**Манифест пока не ведём.** `prompt-composites/README.md` — краткое описание
папки и ссылка на этот гайд. Список композитов с версиями — при необходимости
собирается grep'ом. Если ручной grep начнёт болеть — введём манифест.

## 7. Standalone-паттерн для Behaviors

Behavior используется и как add-on, и как самостоятельная рамка. Чтобы не
держать двух источников:

**Способ A (предпочтительный).** Единственный источник —
`behaviors/<имя>.BEHAVIOR.txt` (форма «Мыслишь как …»). Standalone-версия —
`prompt-composites/<имя>.Standalone.txt`: минимальная обёртка («Ты —
ассистент») + полный текст Behavior. При правке Behavior композит
пересобирается.

**Способ B (допустимый, с оговоркой).** Два файла в `behaviors/`:
`<имя>.BEHAVIOR.txt` и `<имя>.ROLE.txt`, с меткой синхронизации в шапке обоих.
Подробнее — [entity-taxonomy.md](entity-taxonomy.md), §3 и §5.

Способ A — меньше обслуживания. Способ B — привычнее для чтения («Ты — критик»).
Выбор за автором, но метка синхронизации при B обязательна.

## 8. Тестирование

Собранный Composite нужно проверить, прежде чем считать готовым.

1. **Свежий чат.** Вставить композит первым сообщением. Никаких предыдущих
   инструкций — проверяем чистый эффект.
2. **2–3 реальных запроса** из той области, для которой собран композит.
   Не синтетических — реальных, из вашей практики.
3. **Проверить:**
    - стойка не «уплывает» — ответы в дефолте Role, а не в дефолте аддона;
    - Behavior не подавляет Role — Критик критикует, но Психолог остаётся
      Психологом;
    - Skills реально углубляют — без них ответ был бы беднее;
    - Formats применяются — оформление соответствует.
4. **Если что-то не так** — правьте порядок блоков, формулировки, или
   пересмотрите состав. Композит, который не проходит тест, — не готов.


============================================================
## 9. Чек-лист перед созданием

- [ ] Одна стойка? (Role ровно одна, Behaviors не меняют стойку)
- [ ] Все add-on правильного типа? (Skill — knowledge, Behavior — practice,
  Format — оформление)
- [ ] Порядок блоков: Role → база → критичное → Skills → Behaviors → Formats?
- [ ] Имя: Role первая, остальные — по логике сборки?
- [ ] Версии в шапке: composite + встроенные add-on?
- [ ] Версия Composite = самая поздняя из аддонов?
- [ ] Протестирован на 2–3 реальных запросах?


============================================================
## 10. Антипаттерны

- **Две стойки в одном Composite.** Это не композит, а другая роль.
- **Франкенштейн.** Много блоков без логики: «на всякий случай добавлю ещё
  один Skill». Композит — инструмент, а не склад.
- **Устаревшие версии.** Аддон обновился, композит — нет. Grep по `встроено:`
  при правке аддона.
- **Composite для одноразовой задачи.** Разовое — динамически, через обёртку.
- **Wrapper внутри Composite.** Обёртка — для динамики, в статике не нужна.
